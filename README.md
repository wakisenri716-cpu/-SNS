# ジャジバ（観光専用SNS）

観光の情報格差解消と自治体プロモーション支援を目的とした、観光特化型SNSのMVP実装です。企画書の内容に基づき、以下をコア機能として実装しています。

- Instagram/TikTokのリールのような縦スクロール動画フィード（「おすすめ」）。10件ずつ読み込み、下までスクロールすると続きを自動で読み込む（旅行スタイルによる並び替え時は最新100件を一度に表示）
- **リール動画を投稿できるのは自治体アカウント、および自治体に紐づいた企業アカウントのみ**（一般ユーザーは閲覧・いいね・コメントのみ）
- 自治体プロフィール（アクセス方法・宿情報・飲食店・観光情報・OTA外部リンク・投稿一覧）
- 自治体管理ダッシュボード：「投稿」「観光情報」「アクセス方法」「宿情報」「飲食店」のタブに分かれており、「投稿」タブでリール投稿・削除、「観光情報」タブで管轄内の観光スポットを1件ずつ登録・編集・削除できる。ほかに紐づく企業一覧の確認、MaaS起点駅の設定も可能
- 企業管理ダッシュボード（自社が投稿したリールの投稿・編集・削除のみ。自治体プロフィールの編集は不可）
- 投稿の編集：両ダッシュボードの「投稿を編集」から説明文・カテゴリ・場所（場所名と緯度経度）・対応タグを変更できる（動画の差し替えは不可）。緯度経度を両方空にして保存すると、投稿時と同様に場所名から位置を自動設定し直す（Google Maps設定時）。削除は確認ダイアログを経て行う
- コメント：リールの全画面表示でコメントのアイコンを押すと、下からコメント欄が開く（閲覧はだれでも、投稿はログイン時のみ。`GET/POST /api/reels/:id/comments`）。自治体・企業が設定でコメントをオフにしている投稿には書き込めない。コメントは書いた本人と、その投稿を管理する自治体・企業が削除できる（`DELETE /api/reels/:id/comments/:commentId`）
- コメントの通報：ほかの人のコメントは「通報」から理由（スパム・宣伝／誹謗中傷・嫌がらせ／その他）を選んで通報できる（1人1回。`CommentReport` テーブル）。3人から通報されると自動で非表示になり（書いた本人と、その投稿を管理する自治体・企業には「非表示中」として見える）、管理画面の「通報されたコメント」で削除するか、問題なければ「残す」で通報を取り消す（`GET /api/reels/mine/reported-comments`）
- 共有：リールの全画面表示とアクセス画面の「共有」で、その投稿のアクセス画面へのリンクを共有できる（スマホでは端末の共有メニュー、使えない環境ではリンクをコピー）。アイコンだけのボタン（いいね・保存・閉じる等）には読み上げ用の名前を付けている
- お知らせ：自治体・企業アカウントには、自分の投稿へのいいね・コメントがメニューの「お知らせ」に届く（未読数のバッジ付き、スマホではメニューのアイコンに赤い点。`GET /api/notifications`、`backend/src/lib/notifications.ts`）。設定画面の「いいね通知」「コメント通知」をオフにするとその種類は作られない。自分自身の操作では通知せず、いいねの付け外しを繰り返しても1回だけ。コメントが削除されると、そのお知らせも消える。プッシュ通知・メールには未対応で、アプリ内のお知らせのみ。一般ユーザーは投稿しないため、お知らせも通知設定も表示しない
- 旅行者向けのお知らせ：フォローしている自治体・企業が新しく投稿すると、旅行者のお知らせ（スマホは上部のベル、PCは左メニュー）に動画の小さな画像付きで届く（`notifyFollowersOfNewPost`、`backend/src/lib/notifications.ts`）。自治体と企業の両方をフォローしていても1回だけ。設定画面の「フォロー中の新着投稿」でオフにできる（`User.notifyOnNewPost`）
- キーワード検索、ルールベースの「AIレコメンド」。検索では「バリアフリー対応」などの対応タグでも絞り込める（複数選ぶとすべてを満たす投稿のみ。タグだけでも検索可、`GET /api/search?tags=`）。検索結果の投稿をタップするとその投稿のアクセス画面に移動する
- MaaS/OTA連携の土台（下記「外部連携について」参照）
- 初めての人向け：ログインしていない訪問者には、フィード上部に「ジャジバとは」の短い案内と登録への導線を表示（閉じるとその端末では再表示しない）。リンクを共有したときのプレビュー用に、`index.html` に説明文とOGP/Twitterカード（`frontend/public/og-image.png`、1200×630）を設定。OGPのURLは本番ドメイン `https://jaziba.jp/` を前提にしている
- 登録直後のオンボーディング：旅行者が新規登録すると、3ステップ（だれと行くか・好きな場所の種類・バリアフリー／外国語対応）をタップで選ぶ画面（`/welcome`、`frontend/src/pages/OnboardingPage.tsx`）が出て、最初のフィードからその人向けの並びになる。「あとで」で飛ばせ、設定画面の「旅行スタイル」でいつでも変えられる
- リンクのプレビュー：投稿のアクセス画面（`/reels/:id/access`）と自治体ページ（`/municipalities/:id`）のリンクをLINE・X・Facebookなどで共有すると、その投稿の場所名・自治体名と説明文がプレビューに出る。画面はJavaScriptで作られるため、サーバーがこれらのページを返すときだけタイトル・説明・`og:*` を書き換えている（`backend/src/lib/pageMeta.ts`）。プレビュー画像は共通の `og-image.png` のまま
- スマホ対応：タブレット幅（768px）未満では左メニューを隠し、上部バーのメニューアイコンから開くドロワーメニューに切り替わる。画面右側の「しおり」パネルは幅1280px以上でのみ表示されるため、それ未満ではメニューの「しおり」から専用ページ（`/itinerary`）で表示する

## デザイン

SNSとしての使い心地は今どきのアプリに合わせつつ、見た目はジャジバのロゴに揃えています。色はロゴの墨色（`jz-ink` = `#11151D`）と赤い丸（`jz-red` = `#D7202E`）の2色が基本で（`frontend/src/index.css` の `@theme`）、赤は「行き方」ボタン・いいね・フォローなど大事な所だけに使います。ロゴの赤い丸はそのままモチーフにしていて、いま開いているメニューの印、見出しの終わり、読み込み中の表示、ログイン前の案内カードの「日の出」に使っています。自治体アイコンの輪も赤〜朱色のグラデーション。絵文字は使わず、アイコンはすべて lucide-react の線画。フォントは Noto Sans JP（Google Fonts）。

- スマホ：上部はすりガラスのバー（ロゴとメニュー）で、下にスクロールすると隠れ、少しでも上に戻すと再表示。下部は画面から浮いたガラス風のタブバー（アイコンのみ。おすすめ・検索・しおり・マイページ、自治体・企業は 管理・インサイト・お知らせ）。メニューは下から出るシート。タブレット以上は左のサイドバー（選択中は太字）
- フィード：「次の旅先を見つけよう」の見出し、フィード内の自治体の丸いアイコン、文字だけのカテゴリ切り替え（スクロールしても上に固定）。投稿は角の丸い大きなカードで、動画の上に投稿者とフォロー（左上）、場所名と都道府県・赤い「行き方」ボタン・音のオン/オフ（下）を重ねる。カードの影は再生中の動画の色に合わせて光る（同じサイトの動画のみ）。カードの下に いいね数・コメント数・共有・「しおり」ボタン、説明文、タグ（#カテゴリ・#対応タグ）、コメント・「5日前」のような投稿日
- 自治体のページ：プロフィール写真・投稿数・フォロワー数・フォローボタンを上に並べ、その下のタブ（投稿・観光情報・アクセス方法・宿情報・飲食店）を切り替える。投稿は正方形の3列グリッド
- 全画面表示：動画の上に背景なしのアイコン（いいね・コメント・保存・共有）を右側に縦に並べ、左下に投稿者・説明・場所・タグと赤い「アクセス」ボタン
- 動き：投稿をタップすると、カードがそのまま広がって全画面表示になる（View Transitions API。閉じると元のカードに戻る。非対応のブラウザでは普通に切り替え）。投稿はスクロールで画面に入るときにふわっと出てくる（CSSのスクロール連動アニメーション）。動画をダブルタップでいいね（大きなハートが出る）、いいね・保存のボタンは押すと弾み、対応するスマホでは軽く振動する。読み込み中はグレーの形がきらっと光るプレースホルダー、ページ切り替えはふわっと表示、コメント欄やメニューは下からスライド。保存すると「しおりに保存しました／しおりを見る」の通知が出る。端末で「視差効果を減らす」を設定している人には動きを止める
- 動画：同時に再生するのは画面に入った1本だけ（全画面を閉じると元の投稿の続きから）。音は最初は消音で、右下（全画面では右上）のボタンで全動画まとめてオン・オフ。全画面では、タップで一時停止・再開、下端に再生位置のバー。フィードでは動画の縦横比に合わせて表示（縦長は4:5、横長は1.91:1まで）
- ダークモード：端末の設定に合わせて自動で切り替わる（設定画面の「表示モード」で ライト／ダーク／端末に合わせる を選べ、メニューからもワンタップで切り替え可能。選択はその端末にのみ保存）。仕組みは `frontend/src/index.css` の `.dark` で、白とグレーの段階・ロゴの墨色を反転させるだけなので、新しい画面も特に何もしなくても対応する。動画の上や赤いボタンの上（`.on-media` など）は白い文字のまま。ロゴ画像はCSSで白抜きにしている（赤い丸は赤のまま）。表示前に `index.html` の小さなスクリプトで適用するので、開いた瞬間に白く光らない
- アプリとして使える（PWA）：`frontend/public/manifest.webmanifest` と `frontend/public/sw.js`。スマホのブラウザで「ホーム画面に追加」（Android/Chromeではメニューに「アプリとしてホーム画面に追加」が出る）すると、アドレスバーのないアプリとして起動する。アイコンはロゴ画像そのまま（`frontend/public/icons/`）。一度開いた画面は電波がなくても起動でき（投稿や動画などのデータは通信が必要）、オフラインになると通知が出る。インストールしたアプリでは、お知らせの未読数がアイコンにも表示される（対応端末のみ）。Service Worker は本番ビルドでのみ登録し、開発サーバーではキャッシュしない
- 引っ張って更新：スマホでホームの一番上から下に引っ張ると、ロゴの赤い丸が大きくなり、離すと最新の投稿を読み込み直す
- デモ投稿の動画（`backend/seed-assets/*.webm`）は実写の映像がないため、各スポット（松本城・上高地 河童橋・五千尺キッチン・上高地帝国ホテル）をイメージしたイラストのアニメーション（縦長720×1280、8秒）。`backend/seed-assets/source/scenes.html` に描画処理があり、`node backend/seed-assets/source/render.mjs matsumotojo kamikochi gosenjaku teikoku` で作り直せる（Playwright と ffmpeg が必要）

## 公開デプロイ（Render.com）

このリポジトリには [Render](https://render.com) 用の `render.yaml`（Blueprint）を用意しており、フロントエンドのビルド結果をバックエンドの Express プロセスから配信することで、1つのWebサービスとして公開できます。

1. [Render](https://render.com) に無料アカウントを作成し、GitHubアカウントを連携する
2. Renderダッシュボードで **New + → Blueprint** を選択し、このリポジトリ（`claude/tourism-sns-planning-643nty` ブランチ）を指定する
3. `render.yaml` が自動検出されるので、そのまま **Apply** してデプロイを実行する（ビルドには数分かかります）
4. デプロイ完了後に発行されるURL（`https://<サービス名>.onrender.com`）でブラウザからアクセスできます

Blueprintが使えない場合は、**New + → Web Service** で同じリポジトリを選び、以下を手動設定しても同じ内容になります。

- Build Command: `bash render-build.sh`
- Start Command: `node backend/dist/index.js`
- 環境変数：`NODE_ENV=production`, `DATABASE_URL=file:./dev.db`, `UPLOAD_DIR=./uploads`, `JWT_SECRET=<ランダムな文字列>`

**注意（無料プランの制約）**：Renderの無料プランはディスクが永続化されないため、再デプロイやスリープ復帰のたびにSQLiteのデータ（登録した自治体・投稿したリール動画ファイル）はリセットされます。デモ・検証用途として利用し、本番運用する場合はPostgreSQL（データ）＋S3等（動画ファイル）への切り替えを推奨します。

## データモデル（Prisma / backend/prisma/schema.prisma）

- `User`：一般ユーザー / 自治体担当者 / 企業担当者共通のアカウント（`role` で区別：`USER` | `MUNICIPALITY` | `COMPANY`）
- `Municipality`：自治体プロフィール（`User` と1:1）。アクセス方法・宿・飲食店・OTAリンクを保持
- `TourismSpot`：自治体管轄内の観光スポット1件分（`Municipality` に多対1）。名前と説明を持ち、自治体が管理画面からいくつでも登録・編集・削除できる（旧・単一の`tourismInfo`フリーテキストを置き換えたもの）
- `Company`：自治体に紐づく企業アカウント（`User` と1:1、`Municipality` に多対1）。企業は自己登録時に既存の自治体を選んで紐づける
- `Reel`：自治体名義で表示されるリール動画。`companyId` が設定されていれば、その自治体に紐づく企業が投稿したもの
- `Like` / `Comment`：一般ユーザーによるリールへのいいね・コメント

## 権限モデル

- リール投稿は `role: MUNICIPALITY` と `role: COMPANY` のアカウントのみ許可（`backend/src/middleware/auth.ts` の `requireRole`）
- **自治体アカウント**：自分の自治体名義の投稿を全て（紐づく企業が投稿したものも含む）編集・削除でき、自治体プロフィール（アクセス・宿・飲食店・観光情報・OTAリンク）も編集できる
- **企業アカウント**：自社が投稿したリールのみ編集・削除できる。自治体プロフィールの編集は不可
- 一般ユーザーはリール閲覧・いいね・コメントのみ可能
- 企業アカウントは自己登録時に既存の自治体をプルダウンから選んで紐づけます。**自治体側の承認ステップはないため、既存の自治体名を選べば誰でもその自治体名義の投稿権限を持つ企業アカウントを作成できます**。実運用では自治体による承認フローや招待制への変更を推奨します。

## 外部連携について（重要）

企画書ではMaaS（交通情報連携）とOTA（宿・航空券予約）連携が構想されていますが、実際の外部API契約・APIキーがない状態のため、本実装では以下の方針で「差し替え可能な形」にしています。

- **OTA連携**（`backend/src/services/otaProvider.ts`）：じゃらん/楽天トラベル/Booking.com等への外部検索リンクを自動生成して自治体プロフィールに表示します。自治体側で実際の提携リンクに上書きすることも可能です（プロフィール編集画面）。実際のOTA APIと契約できた場合は、この関数を実APIコールに差し替えるだけで組み込めます。
- **MaaS連携**（`backend/src/services/maasProvider.ts`）：リールに紐づく場所情報までの、自治体の「起点駅」からの推定所要時間を表示します。`GOOGLE_MAPS_API_KEY` が設定されていれば **Google Maps Platform の実API**（Geocoding + Directions）で実際の距離・所要時間を計算し、未設定時や計算失敗時は自動的に「モックデータ」（決定的な仮の所要時間）にフォールバックします。モック使用時は画面上に必ず「交通情報は仮データ」と表示されるので、ユーザーはどちらのデータか判別できます。設定方法・既知の制約は次の「Google Maps連携のセットアップ」を参照してください。
- 決済機能（宿泊予約や広告出稿の決済）は未実装です。実装には決済代行事業者との契約が必要なため、現段階ではスコープ外としています。

### Google Maps連携のセットアップ（MaaS機能の実データ化）

MaaS機能を実際の地図・経路データで動かすには、Google Maps Platform の **Geocoding API**・**Directions API**・**Static Maps API** を有効化したAPIキーが必要です（Static Mapsはリールのアクセスページで経路のプレビュー画像を表示するために使います）。キーがない状態でもアプリは正常に動作します（自動的にモックデータ・地図なし表示にフォールバックします）。

1. [Google Cloud Console](https://console.cloud.google.com/) にアクセスし、Googleアカウントでログインしてプロジェクトを新規作成する（既存プロジェクトでも可）
2. 請求先アカウント（クレジットカード登録）を設定する。Google Maps Platformは毎月 $200 分の無料クレジットがあり、このアプリの検証用途であれば通常無料枠内に収まります
3. 左メニュー「APIとサービス → ライブラリ」から以下の3つを検索して有効化する
   - **Geocoding API**（地名・住所 → 緯度経度への変換）
   - **Directions API**（2地点間の距離・所要時間の取得）
   - **Static Maps API**（経路プレビュー画像の生成）
4. 「APIとサービス → 認証情報」→「認証情報を作成」→「APIキー」でキーを発行する
5. 発行したキーを選択し、「APIの制限」で上記3つのAPI（Geocoding API, Directions API, Static Maps API）のみに制限する（不要な課金・悪用防止のため必須）。「アプリケーションの制限」は、サーバーサイドからのみ呼び出すキーなので「なし」のままで問題ありません
6. 発行されたキーをバックエンドの環境変数 `GOOGLE_MAPS_API_KEY` に設定する
   - ローカル開発: `backend/.env` に `GOOGLE_MAPS_API_KEY=<発行されたキー>` を追記
   - Render: ダッシュボードの対象サービス → Environment → `GOOGLE_MAPS_API_KEY` を追加

**セキュリティ上の注意**：このキーはバックエンド（サーバー側）でのみ使用し、フロントエンドのコードや `VITE_` 系の環境変数には絶対に含めないでください。フロントエンドに含めるとキーが公開され、第三者に不正利用（高額請求）されるおそれがあります。

設定後、自治体アカウントの管理画面（`/dashboard`）で「MaaS（交通案内）起点駅」欄に最寄り駅・バス停名を入力すると、その地点を起点としてリールの位置情報までの推定所要時間が計算されるようになります。未入力の場合や、キー未設定・API呼び出し失敗時は自動的にモックデータが使われます。

**既知の制約（重要）**：Google MapsのDirections/Routes APIは、`mode=transit`（電車・バスの乗換案内）について日本国内の経路データを一般的なAPIキーには提供していません（検証の結果、京都・東京・大阪の主要駅間で一貫して`ZERO_RESULTS`となることを確認済み。Googleマップアプリ自体が表示する日本の乗換案内は、この公開APIとは別のデータ提携によるものです）。そのため本実装では、実際の乗換時間の代わりに、起点駅からの**徒歩または車移動の実測距離・所要時間**（`backend/src/services/googleMaps.ts` の `getRouteEstimate`：3km以内は徒歩、それ以上は車移動で計算）を使用しています。正確な「電車で何分・何線」といった乗換案内が必要な場合は、駅すぱあとAPI（ヴァル研究所）やNAVITIME APIなど、日本の乗換案内に特化した外部APIへの切り替えを検討してください（`maasProvider.ts` の `getTransitSuggestion` を差し替えるだけで組み込める設計です）。

### AIに旅を相談（AIコンシェルジュ）

ホームと検索画面の「AIに旅を相談」から、「家族で雪景色を見たい」「カップルでおいしいそば」のように、行きたい旅を文章や音声（マイクボタン。ブラウザの音声認識を使用し、対応ブラウザでのみ表示）で伝えると、ジャジバの投稿から合いそうな場所を選び、理由と「行き方」「しおり」ボタン付きで表示します（`POST /api/concierge`、`backend/src/services/concierge.ts`、画面は `frontend/src/components/ConciergeSheet.tsx`）。検索画面の検索欄にも音声入力を付けています。

- **AIモード**：バックエンドに `ANTHROPIC_API_KEY` を設定すると、Claude（`claude-opus-5-5`、構造化出力でJSONを返す）が最新60件の投稿の中から最大5件を選び、一言の理由と返事を書きます。選べる投稿IDはスキーマで限定しているので、実在しない場所を勧めることはなく、理由も投稿の説明・場所・カテゴリ・タグに書かれていることだけを使うよう指示しています（営業時間・料金・バリアフリー可否などの、投稿に書かれていない事実は付け加えない）。安全上の理由でモデルが回答を断った場合はAnthropicの推奨モデルで自動的にやり直す設定（`fallbacks: "default"`）にしています。1IPあたり10分20回まで
- **キーワードモード**：キーが未設定、または呼び出しに失敗した場合は、カテゴリ・対応タグ・地名のキーワード一致で探します。この場合は画面に「AIは未設定」「キーワードの一致で探しています」と必ず表示し、AIの回答のようには見せません
- キーの設定：ローカルは `backend/.env` に `ANTHROPIC_API_KEY=<キー>`、Renderはサービスの Environment に `ANTHROPIC_API_KEY` を追加（キーは https://console.anthropic.com で発行。Google Mapsのキーと同じく、フロントエンドには絶対に含めない）。利用量に応じてAnthropicの料金がかかります

### プッシュ通知

設定の「プッシュ通知（この端末）」をオンにすると、お知らせ（フォロー中の新しい投稿、いいね・コメント）がアプリを閉じていても端末に届きます（Web Push。通知の文言は端末の表示言語）。iPhoneでは、Safariの「ホーム画面に追加」で入れたアプリで使えます。ログアウトするとその端末には届かなくなります。
- 送信用の鍵（VAPID）は、環境変数 `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` があればそれを使い、なければ初回に自動で作ってデータベース（`AppSetting`）に保存します。**データベースが作り直されると鍵も変わり、それまでのプッシュ登録は使えなくなる**ので、本番では `npx web-push generate-vapid-keys` で作った鍵をRenderの Environment に設定しておくのがおすすめです（任意で `VAPID_SUBJECT` に連絡先 `mailto:...` または `https://...`）
- 届かなくなった端末（プッシュサービスが404/410を返したもの）は自動で登録を消します

### アクセスプランナー（自治体プロフィールの「アクセス方法」タブ）

自治体プロフィールページの「アクセス方法」タブから、訪問者が自分の出発地点（駅名など）を自由に入力し、その自治体の起点駅までの**所要時間・移動手段・概算運賃**を確認できます（`GET /api/municipalities/:id/access-plan`）。既存の「リールごとの自動MaaS表示」と違い、こちらは訪問者がボタンを押した時だけAPIを呼ぶ一度きりの操作なので、閲覧のたびに自動発生する既存のDirections API呼び出しとは別枠で、コスト面のリスクは低めです。

運賃は実際の運賃データを取得しているわけではなく、距離に応じた**簡易な概算**（`maasProvider.ts` の `estimateFareYen`：¥150基礎運賃＋距離に応じた1kmあたりの単価）です。画面上にも「※運賃は概算です」と明記しています。正確な運賃が必要な場合も、上記の乗換案内特化APIへの切り替えが前提になります。

各リールの再生画面にも同様の「アクセス」ボタンがあり、こちらは自治体の起点駅ではなく**その投稿の場所そのもの**を目的地として計算します（`GET /api/reels/:id/access-plan`）。

どちらの画面でも出発日時（`<input type="datetime-local">`）を指定でき、車移動の場合はGoogle Directions APIの`departure_time`パラメータにより**実際の予測交通状況を反映した所要時間**が得られます。ただし、この機能は電車・バスの実際の発着時刻表とは連動していません（本アプリはそのデータを持っていません）。到着予定時刻は、あくまで「指定した出発日時＋徒歩/車移動の所要時間」の計算値であり、画面にも常にその旨のディスクレーマーを表示しています。実際の乗換時刻表が必要な場合は、既出の駅すぱあと／NAVITIME等への切り替えが前提です。

リールのアクセスページでは電車・バス・車・タクシー・徒歩の5通りを並べて比較でき（`frontend/src/lib/accessModeEstimate.ts`）、各カードの詳細を開くと経路プレビュー画像も表示されます（`GET /api/reels/:id/access-map`）。この画像はGoogle Directions APIが返す実際の道路上のルート（polyline）をStatic Maps API経由で描画したものですが、Directionsが使えなかった場合は出発地点〜目的地を結ぶ直線にフォールバックします（実際の道なりではない点に注意）。Static Maps APIが未設定・呼び出し失敗の場合は、画面側で簡易な概略図（点線のプレースホルダー）に自動で切り替わります。5モードのうち実際にAPIで取得できるのは徒歩または車のいずれか1つだけなので、電車・バス・タクシーの時間や運賃は距離ベースの概算です（画面にもその旨明記）。

自治体・企業アカウントは `/insights` から、自分（自治体の場合は紐づく企業の投稿も含む）の投稿の再生数・いいね数・コメント数と、カテゴリ別・投稿別の内訳を確認できます。

さらに、Instagramの「オーディエンス」に相当する視聴者の**国籍・年代別の内訳**も表示します。これは `ReelView` テーブル（`backend/prisma/schema.prisma`）に記録される閲覧ログと、`User.nationality` / `User.birthYear`（登録時またはSettingsから**任意**で入力）を突き合わせて集計したものです（`GET /api/reels/mine/demographics`）。ログアウト中の視聴や、国籍・生まれた年を登録していないアカウントによる視聴は「不明」として分類されます — Instagramなどと同様、自己申告データがある範囲でしか属性を特定できない設計です。

メールアドレスからは年齢・国籍いずれも推測できないため（ドメインだけでは国籍の判定精度が低すぎる）、新規登録画面では `geoip-lite`（オフラインのIP→国データベース、外部API呼び出し・APIキー不要）でIPアドレスから国籍欄の初期値をおおまかに推定し、プルダウンに仮選択した状態で表示します（`backend/src/services/geoLookup.ts`、`GET /api/auth/suggest-nationality`）。あくまで初期値の提案であり、本人はいつでも変更・未選択にでき、保存もされません。生まれた年はこの方法でも取得できないため、引き続き完全に自己申告です。設定画面のプロフィール欄からも、国籍・生まれた年はいつでも編集できます（一般ユーザーアカウントのみ）。

## しおり（保存した場所をつなぐ旅程）

一般ユーザーアカウントでログインすると、幅の広い画面ではページ右側に「しおり」パネルが常時表示されます（`frontend/src/components/ItineraryRail.tsx`。自治体・企業アカウントには表示されません）。それより狭い画面ではメニューの「しおり」（`/itinerary`）から開きます。リールの保存機能で保存した投稿をつなぎ、時刻入りの行程表にします（`GET /api/reels/itinerary`）。位置情報を持たない投稿は経路に含められません。

- **並び替え・削除**：各スポットの↑↓で順番を入れ替えられます（`PUT /api/reels/itinerary/order`、`SavedReel.position`）。並び替える前は保存した順で、並び替え後に新しく保存した投稿は末尾に入ります。はしおりから外す操作で、保存自体を解除します
- **滞在時間**：スポットごとに滞在時間（0〜240分）を選べます（`PATCH /api/reels/:id/save`、`SavedReel.stayMinutes`、初期値60分）
- **出発地点・出発時刻**：しおり上部で設定します（`PUT /api/reels/itinerary/settings`、`User.itineraryOrigin`／`itineraryStartTime`）。出発時刻＋移動時間＋滞在時間を足し合わせて、各スポットの「◯時◯分着 → ◯時◯分発」と最後の場所の出発時刻を表示します（日付をまたぐと「翌」）
- 出発地点から最初のスポットまでの移動時間は、出発地点をジオコーディングできた場合（Google Maps設定時）のみ含めます。位置を特定できない場合は名前ベースの仮データでごまかさず、移動時間を含めていない旨を表示し、出発時刻に最初のスポットへ着く想定で計算します（仮データが数時間ずれると、以降の時刻がすべてずれるため）
- しおりは画面の端に常駐していて、他の画面での保存・保存解除にも追従します（`frontend/src/lib/savesChanged.ts`）。逆に、しおりで外した投稿はフィードなどの保存表示にも反映されます

区間ごとの移動時間は、既存のアクセスプランナーと同じ`getTransitSuggestion`（`maasProvider.ts`）をそのまま再利用しています。2つの保存済み投稿は互いに位置情報（緯度経度）を持っているため、ジオコーディングなしで直接Directions APIに渡せます。Google Maps未設定時や実データが取得できない場合は仮データにフォールバックし、「仮データ」バッジで明示します。両端の座標が分かっている場合の仮データは、直線距離をもとにした概算です（道のりは直線の約1.4倍と仮定し、2km以内は徒歩4.5km/h、それより遠い場合は徒歩10分＋電車・バス平均30km/h）。以前は場所の名前から決まる数値だったため、30mしか離れていない場所の間が50分になることがありました。

「リスト／地図」の切り替えで、保存した場所を線でつないだ簡易図も表示できます（`frontend/src/components/SchematicRouteMap.tsx`）。実際の地図データ（道路・地形）は使用しておらず、各投稿の緯度経度を単純に正規化して配置しただけの模式図です（相対的な位置関係は実座標に基づいていますが、あくまで概略図としてご利用ください）。同じコンポーネントは、リールのアクセス詳細画面（`ReelAccessPage`の「詳しく見る」）でGoogle Static Maps APIの画像が取得できなかった場合のフォールバック表示にも使われています。

## 自治体・企業向け：旅行計画への効果（インサイト）

インサイト画面（`/insights`）に、投稿が実際の旅行計画にどれだけつながっているかを追加しています（`GET /api/reels/mine/trip-planning`）。

- 保存（しおり）数：各投稿を旅行者がブックマークした数。しおりはブックマークから作られるため、「行き先候補に入れた」人数の目安になります。投稿ごとの一覧にも保存数として表示し、保存数順に並べ替えられます
- CSVで保存：投稿ごとの数値（投稿日・場所・説明文・カテゴリ・投稿者・再生数・いいね数・コメント数・保存数・実測の記録数）をCSVでダウンロードできる。Excelで日本語が文字化けしないよう先頭にBOMを付け、投稿者が書いた説明文が `=` などで始まっていてもExcelの数式として実行されないよう無害化している（`frontend/src/lib/csv.ts`）
- 実測の記録数：旅行者が記録した「実際にかかった時間」の件数（⏱）
- 旅行者はどこから来ているか：実測の記録の出発地点と、使った移動手段の内訳。上記のプライバシーのルールにより、2人以上が記録した出発地点だけを表示し、それ以外は件数のみ表示します

## 旅行スタイルにあわせた「おすすめ」

一般ユーザーは設定画面の「旅行スタイル」で、よく一緒に行く人（ひとり／カップル・夫婦／家族・子連れ／友人グループ）、興味のあるカテゴリ、バリアフリー対応・外国語対応を優先するかを設定できます（`User.travelCompanion` ほか、`PUT /api/auth/me`）。設定があると、フィードの「おすすめ」タブ（カテゴリ未選択時）の並び順が変わります（`backend/src/lib/personalize.ts`）。

- 各投稿の「対応・おすすめ相手タグ」とカテゴリを設定と照らし合わせて点数化し、点数の高い順に並べます（同点なら新しい順）。重みはバリアフリー4・外国語対応3・興味のあるカテゴリ3・同行者2で、移動の必要条件（バリアフリー）を好み（カテゴリ）より優先しています。一致しない投稿も非表示にはせず、後ろに並ぶだけです
- 並び順をブラックボックスにしないよう、上位に来た理由をリールの全画面表示に「おすすめ理由：興味のあるカテゴリ（文化）・「家族・子連れ」の旅行向け」のように表示します。フィード上部にも、並び替え中かどうかと設定画面へのリンクを出します
- 並べ替えには候補全体が必要なため、パーソナライズ時は最新100件を1ページで返します（通常時は従来どおり新しい順10件）
- ログインしていない場合・カテゴリタブ選択時・旅行スタイル未設定時は、従来どおり新しい順です。検索画面の「AIレコメンド」（人気度ベース）とは別の仕組みです

## 対応・おすすめ相手タグ

投稿ごとに「バリアフリー対応」「家族・子連れ向け」「カップル向け」「友人グループ向け」「外国語対応」を付けられます（`Reel.travelerTags`、カンマ区切り文字列。値の一覧は `backend/src/types.ts` の `TRAVELER_TAGS`）。自治体・企業が投稿時に選ぶか、ダッシュボードの投稿の「投稿を編集」から後から変更できます（`PUT /api/reels/:id`）。付けたタグはリールの全画面表示とアクセス画面に表示されます。

- 「バリアフリー対応」「外国語対応」は実際の設備・対応状況についての事実の主張なので、編集画面に「確認したうえで設定してください」と注記しています
- デモ用シードには主観的な「誰向けか」のタグ（家族・カップル・友人）だけを入れ、バリアフリー・外国語対応は入れていません（実在施設について未確認の主張をしないため）

## 近くの観光スポット

リールのアクセス画面（`/reels/:id/access`）の下部に、その投稿の近く（半径50km以内）にある他の投稿を近い順に最大6件表示します（`frontend/src/components/NearbySpots.tsx`、`GET /api/reels/:id/nearby`）。投稿した自治体・企業に関係なく、位置情報（緯度経度）を持つすべての投稿が対象です。距離は各投稿の緯度経度からの直線距離（haversine）で、道のりの距離ではありません。上部のカテゴリ（自然・文化・アクティビティー・宿・飲食店）で絞り込めるので、「近くの宿」「近くの飲食店」だけを探すこともできます（`?category=`）。カードをクリックするとその投稿のアクセス画面に移動するので、「1つ見つけた場所 → 近くの別の場所 → そこへの行き方」と続けて調べられます。位置情報を持たない投稿では空表示になります。

自治体の「観光情報」に登録された観光スポットのうち位置（緯度経度）を持つものも、「自治体の観光情報より」として近い順に表示します（カテゴリが無いため「すべて」のときのみ。タップでその自治体のページへ）。スポットの位置は、ダッシュボードの観光情報タブで緯度経度を入力するか、両方空にしておくとスポット名＋自治体名からGoogle Mapsで自動的に探します（`backend/src/lib/locateTourismSpot.ts`。見つからない・未設定のときは推測で埋めず「位置なし」のまま）。デモ用シードでは河童橋のみ座標を持たせ、大正池は確かな座標を確認できなかったため、Google Maps設定時の自動検索に任せています。

その下には、投稿した自治体の「宿情報」「飲食店」の内容と宿の予約サイト検索リンク（プロフィールと同じもの）を表示し、プロフィールへのリンクも置いています（`frontend/src/components/MunicipalityStayInfo.tsx`）。投稿を見つけた旅行者が、自治体のプロフィールを探しに行かなくても宿・飲食店の情報までたどれるようにするためです。

デモ用シードには、この機能が初回起動直後から確認できるよう、松本市の投稿を4件（松本城・上高地 河童橋・五千尺キッチン・上高地帝国ホテル）入れています。動画はいずれも実写素材がないため、場所名を表示するだけのプレースホルダー（`backend/seed-assets/`）です。

## みんなの実測（実際にかかった時間の記録とポイント）

リールのアクセス画面に「実際にかかった時間（みんなの実測）」欄があります（`frontend/src/components/TravelReportSection.tsx`）。実際にその場所へ行った一般ユーザーが、出発地点・移動手段（電車／バス／車／タクシー／徒歩）・かかった時間を記録すると10ポイントもらえます（`POST /api/reels/:id/travel-reports`、一般ユーザーのみ）。

- 記録は「ユーザー × 投稿 × 移動手段」ごとに1件（`TravelTimeReport`、ユニーク制約）。同じ組み合わせで記録し直すと時間が上書きされるだけで、ポイントは増えません（同じ記録の繰り返しでポイントを稼げないようにするため）
- 集まった記録は**出発地点＋移動手段ごと**に平均して表示します（`GET /api/reels/:id/travel-reports`）。出発地点が違うと所要時間は大きく変わるため、全員分をまとめた1つの平均は出しません。出発地点は入力された文字列（前後の空白などを整えたもの）で一致判定するので、「小田原駅」と「小田原」は別の出発地点として扱われます
- アクセスを検索した出発地点と同じ地点からの記録がある場合は、該当する移動手段のカードにも「みんなの実測 平均◯分・◯件」を表示します
- ポイントは記録件数から都度計算しています（`backend/src/lib/points.ts`、残高は保存していません）。マイページで合計を確認できます（`GET /api/auth/me/points`）。**ポイントの使い道（クーポン等）はまだ無く、画面上でも試作である旨を表示しています**
- 記録はユーザーの自己申告で、正確さは検証していません。デモ用シードにも、実際の記録と誤解されないよう実測データは入れていません
- **出発地点のプライバシー**：出発地点は自由入力のため、自宅の住所などが入力される可能性があります。そのため、**2人以上の異なるユーザーが同じ出発地点を記録するまでは、その出発地点を誰にも表示しません**（`backend/src/lib/travelReports.ts` の `MIN_REPORTERS_PER_ORIGIN`）。非表示の記録は件数だけ表示し、記録した本人には「あなたの記録」として常に表示します。入力欄にも、他のユーザーに表示されるので駅名などを入力するよう注記しています。同じルールを自治体向けインサイトにも適用しています

## 不正利用対策（回数制限）

パスワードの総当たりやスパムを防ぐため、IPアドレスごとに回数制限をかけています（`backend/src/middleware/rateLimit.ts`、`express-rate-limit`）。上限を超えると429とメッセージを返します。

- ログイン：失敗が15分に10回まで（成功したログインは数えないため、同じネットワークの他の人の通常利用で締め出されることはない）
- アカウント登録（旅行者・自治体・企業）：1時間に10回まで
- コメント・実測の記録：10分に30回まで
- お問い合わせ：1時間に5回まで
- 共有されたしおりの表示：10分に60回まで

カウンターはメモリ上にあるためサーバー再起動でリセットされます（1台構成の前提）。利用者のIPを正しく得るため、`trust proxy` はRenderの前段プロキシ1段分だけを信頼する設定です（`true` にすると、利用者が `X-Forwarded-For` ヘッダーを偽ってIPを詐称し、制限をすり抜けられてしまうため）。CDNなどプロキシが増える場合は環境変数 `TRUST_PROXY_HOPS` で段数を指定してください。

## 多言語対応

i18next / react-i18next を使い、日本語・英語・中国語・韓国語に対応しています（`frontend/src/locales/`）。対応範囲はアプリのUI文言（ボタン・メニュー・フォームラベルなど）のみで、自治体が入力する説明文・投稿キャプション・都道府県名などのユーザー/実体データは翻訳されません。初めて開いたときは、ブラウザの言語設定（英語・中国語・韓国語なら、その言語）で表示します（`frontend/src/lib/detectLanguage.ts`）。設定画面（`/settings`）の「表示言語」から切り替えでき、選択言語は端末のlocalStorageに保存されます。


画面ごとのプログラムは、トップのフィード以外は初めて開いたときに読み込みます（`React.lazy`、`frontend/src/App.tsx`）。翻訳ファイルも日本語だけを最初に読み込み、英語・中国語・韓国語は選んだときに読み込みます（`frontend/src/i18n.ts`）。前回英語などを選んでいた人には、読み込みが終わるまでの一瞬だけ日本語が表示されます。
