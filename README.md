# ジャジバ（観光専用SNS）

観光の情報格差解消と自治体プロモーション支援を目的とした、観光特化型SNSのMVP実装です。企画書の内容に基づき、以下をコア機能として実装しています。

- Instagram/TikTokのリールのような縦スクロール動画フィード（「おすすめ」）
- **リール動画を投稿できるのは自治体アカウント、および自治体に紐づいた企業アカウントのみ**（一般ユーザーは閲覧・いいね・コメントのみ）
- 自治体プロフィール（アクセス方法・宿情報・飲食店・観光情報・OTA外部リンク・投稿一覧）
- 自治体管理ダッシュボード：「投稿」「観光情報」「アクセス方法」「宿情報」「飲食店」のタブに分かれており、「投稿」タブでリール投稿・削除、「観光情報」タブで管轄内の観光スポットを1件ずつ登録・編集・削除できる。ほかに紐づく企業一覧の確認、MaaS起点駅の設定も可能
- 企業管理ダッシュボード（自社が投稿したリールの投稿・削除のみ。自治体プロフィールの編集は不可）
- キーワード検索、ルールベースの「AIレコメンド」
- MaaS/OTA連携の土台（下記「外部連携について」参照）

## 構成

```
backend/   Express + TypeScript + Prisma(SQLite) API サーバー
frontend/  React(Vite) + TypeScript + Tailwind CSS の SPA
```

フロントエンドとバックエンドは別プロジェクト・別プロセスで、フロントは `/api` 宛のリクエストを Vite の dev proxy でバックエンドに転送します。

## デモ用シードデータ

`backend/src/seed.ts` は、自治体テーブルが空のときに自動的にデモ自治体「松本市」と、上高地を紹介するリール1件を作成します。バックエンド起動時（`npm run dev` / 本番起動どちらも）に自動実行されるので、特別な操作なしにフィードが埋まった状態で確認できます（Renderの無料プランでデータがリセットされた場合も、次回起動時に自動で再投入されます）。

- デモ自治体アカウント：`demo-matsumoto@example.com` / `password123`
- 手動で再シードしたい場合は `cd backend && npm run seed`（既にデータがある場合は何もしません）

## 公開デプロイ（Render.com）

このリポジトリには [Render](https://render.com) 用の `render.yaml`（Blueprint）を用意しており、フロントエンドのビルド結果をバックエンドの Express プロセスから配信することで、1つのWebサービスとして公開できます。

1. [Render](https://render.com) に無料アカウントを作成し、GitHubアカウントを連携する
2. Renderダッシュボードで **New + → Blueprint** を選択し、このリポジトリ（`claude/tourism-sns-planning-643nty` ブランチ）を指定する
3. `render.yaml` が自動検出されるので、そのまま **Apply** してデプロイを実行する（ビルドには数分かかります）
4. デプロイ完了後に発行されるURL（`https://<サービス名>.onrender.com`）でブラウザからアクセスできます

Blueprintが使えない場合は、**New + → Web Service** で同じリポジトリを選び、以下を手動設定しても同じ内容になります。

- Build Command: `bash render-build.sh`
- Start Command: `node backend/dist/index.js`
- 環境変数：`NODE_ENV=production`, `DATABASE_URL=file:./dev.db`, `UPLOAD_DIR=./uploads`, `JWT_SECRET=<ランダムな文字列>`

**注意（無料プランの制約）**：Renderの無料プランはディスクが永続化されないため、再デプロイやスリープ復帰のたびにSQLiteのデータ（登録した自治体・投稿したリール動画ファイル）はリセットされます。デモ・検証用途として利用し、本番運用する場合はPostgreSQL（データ）＋S3等（動画ファイル）への切り替えを推奨します。

## データモデル（Prisma / backend/prisma/schema.prisma）

- `User`：一般ユーザー / 自治体担当者 / 企業担当者共通のアカウント（`role` で区別：`USER` | `MUNICIPALITY` | `COMPANY`）
- `Municipality`：自治体プロフィール（`User` と1:1）。アクセス方法・宿・飲食店・OTAリンクを保持
- `TourismSpot`：自治体管轄内の観光スポット1件分（`Municipality` に多対1）。名前と説明を持ち、自治体が管理画面からいくつでも登録・編集・削除できる（旧・単一の`tourismInfo`フリーテキストを置き換えたもの）
- `Company`：自治体に紐づく企業アカウント（`User` と1:1、`Municipality` に多対1）。企業は自己登録時に既存の自治体を選んで紐づける
- `Reel`：自治体名義で表示されるリール動画。`companyId` が設定されていれば、その自治体に紐づく企業が投稿したもの
- `Like` / `Comment`：一般ユーザーによるリールへのいいね・コメント

## 権限モデル

- リール投稿は `role: MUNICIPALITY` と `role: COMPANY` のアカウントのみ許可（`backend/src/middleware/auth.ts` の `requireRole`）
- **自治体アカウント**：自分の自治体名義の投稿を全て（紐づく企業が投稿したものも含む）編集・削除でき、自治体プロフィール（アクセス・宿・飲食店・観光情報・OTAリンク）も編集できる
- **企業アカウント**：自社が投稿したリールのみ編集・削除できる。自治体プロフィールの編集は不可
- 一般ユーザーはリール閲覧・いいね・コメントのみ可能
- 企業アカウントは自己登録時に既存の自治体をプルダウンから選んで紐づけます。**自治体側の承認ステップはないため、既存の自治体名を選べば誰でもその自治体名義の投稿権限を持つ企業アカウントを作成できます**。実運用では自治体による承認フローや招待制への変更を推奨します。

## 外部連携について（重要）

企画書ではMaaS（交通情報連携）とOTA（宿・航空券予約）連携が構想されていますが、実際の外部API契約・APIキーがない状態のため、本実装では以下の方針で「差し替え可能な形」にしています。

- **OTA連携**（`backend/src/services/otaProvider.ts`）：じゃらん/楽天トラベル/Booking.com等への外部検索リンクを自動生成して自治体プロフィールに表示します。自治体側で実際の提携リンクに上書きすることも可能です（プロフィール編集画面）。実際のOTA APIと契約できた場合は、この関数を実APIコールに差し替えるだけで組み込めます。
- **MaaS連携**（`backend/src/services/maasProvider.ts`）：リールに紐づく場所情報までの、自治体の「起点駅」からの推定所要時間を表示します。`GOOGLE_MAPS_API_KEY` が設定されていれば **Google Maps Platform の実API**（Geocoding + Directions）で実際の距離・所要時間を計算し、未設定時や計算失敗時は自動的に「モックデータ」（決定的な仮の所要時間）にフォールバックします。モック使用時は画面上に必ず「交通情報は仮データ」と表示されるので、ユーザーはどちらのデータか判別できます。設定方法・既知の制約は次の「Google Maps連携のセットアップ」を参照してください。
- 決済機能（宿泊予約や広告出稿の決済）は未実装です。実装には決済代行事業者との契約が必要なため、現段階ではスコープ外としています。

### Google Maps連携のセットアップ（MaaS機能の実データ化）

MaaS機能を実際の地図・経路データで動かすには、Google Maps Platform の **Geocoding API**・**Directions API**・**Static Maps API** を有効化したAPIキーが必要です（Static Mapsはリールのアクセスページで経路のプレビュー画像を表示するために使います）。キーがない状態でもアプリは正常に動作します（自動的にモックデータ・地図なし表示にフォールバックします）。

1. [Google Cloud Console](https://console.cloud.google.com/) にアクセスし、Googleアカウントでログインしてプロジェクトを新規作成する（既存プロジェクトでも可）
2. 請求先アカウント（クレジットカード登録）を設定する。Google Maps Platformは毎月 $200 分の無料クレジットがあり、このアプリの検証用途であれば通常無料枠内に収まります
3. 左メニュー「APIとサービス → ライブラリ」から以下の3つを検索して有効化する
   - **Geocoding API**（地名・住所 → 緯度経度への変換）
   - **Directions API**（2地点間の距離・所要時間の取得）
   - **Static Maps API**（経路プレビュー画像の生成）
4. 「APIとサービス → 認証情報」→「認証情報を作成」→「APIキー」でキーを発行する
5. 発行したキーを選択し、「APIの制限」で上記3つのAPI（Geocoding API, Directions API, Static Maps API）のみに制限する（不要な課金・悪用防止のため必須）。「アプリケーションの制限」は、サーバーサイドからのみ呼び出すキーなので「なし」のままで問題ありません
6. 発行されたキーをバックエンドの環境変数 `GOOGLE_MAPS_API_KEY` に設定する
   - ローカル開発: `backend/.env` に `GOOGLE_MAPS_API_KEY=<発行されたキー>` を追記
   - Render: ダッシュボードの対象サービス → Environment → `GOOGLE_MAPS_API_KEY` を追加

**セキュリティ上の注意**：このキーはバックエンド（サーバー側）でのみ使用し、フロントエンドのコードや `VITE_` 系の環境変数には絶対に含めないでください。フロントエンドに含めるとキーが公開され、第三者に不正利用（高額請求）されるおそれがあります。

設定後、自治体アカウントの管理画面（`/dashboard`）で「MaaS（交通案内）起点駅」欄に最寄り駅・バス停名を入力すると、その地点を起点としてリールの位置情報までの推定所要時間が計算されるようになります。未入力の場合や、キー未設定・API呼び出し失敗時は自動的にモックデータが使われます。

**既知の制約（重要）**：Google MapsのDirections/Routes APIは、`mode=transit`（電車・バスの乗換案内）について日本国内の経路データを一般的なAPIキーには提供していません（検証の結果、京都・東京・大阪の主要駅間で一貫して`ZERO_RESULTS`となることを確認済み。Googleマップアプリ自体が表示する日本の乗換案内は、この公開APIとは別のデータ提携によるものです）。そのため本実装では、実際の乗換時間の代わりに、起点駅からの**徒歩または車移動の実測距離・所要時間**（`backend/src/services/googleMaps.ts` の `getRouteEstimate`：3km以内は徒歩、それ以上は車移動で計算）を使用しています。正確な「電車で何分・何線」といった乗換案内が必要な場合は、駅すぱあとAPI（ヴァル研究所）やNAVITIME APIなど、日本の乗換案内に特化した外部APIへの切り替えを検討してください（`maasProvider.ts` の `getTransitSuggestion` を差し替えるだけで組み込める設計です）。

### アクセスプランナー（自治体プロフィールの「アクセス方法」タブ）

自治体プロフィールページの「アクセス方法」タブから、訪問者が自分の出発地点（駅名など）を自由に入力し、その自治体の起点駅までの**所要時間・移動手段・概算運賃**を確認できます（`GET /api/municipalities/:id/access-plan`）。既存の「リールごとの自動MaaS表示」と違い、こちらは訪問者がボタンを押した時だけAPIを呼ぶ一度きりの操作なので、閲覧のたびに自動発生する既存のDirections API呼び出しとは別枠で、コスト面のリスクは低めです。

運賃は実際の運賃データを取得しているわけではなく、距離に応じた**簡易な概算**（`maasProvider.ts` の `estimateFareYen`：¥150基礎運賃＋距離に応じた1kmあたりの単価）です。画面上にも「※運賃は概算です」と明記しています。正確な運賃が必要な場合も、上記の乗換案内特化APIへの切り替えが前提になります。

各リールの再生画面にも同様の「🧭 アクセス」ボタンがあり、こちらは自治体の起点駅ではなく**その投稿の場所そのもの**を目的地として計算します（`GET /api/reels/:id/access-plan`）。

どちらの画面でも出発日時（`<input type="datetime-local">`）を指定でき、車移動の場合はGoogle Directions APIの`departure_time`パラメータにより**実際の予測交通状況を反映した所要時間**が得られます。ただし、この機能は電車・バスの実際の発着時刻表とは連動していません（本アプリはそのデータを持っていません）。到着予定時刻は、あくまで「指定した出発日時＋徒歩/車移動の所要時間」の計算値であり、画面にも常にその旨のディスクレーマーを表示しています。実際の乗換時刻表が必要な場合は、既出の駅すぱあと／NAVITIME等への切り替えが前提です。

リールのアクセスページでは電車・バス・車・タクシー・徒歩の5通りを並べて比較でき（`frontend/src/lib/accessModeEstimate.ts`）、各カードの詳細を開くと経路プレビュー画像も表示されます（`GET /api/reels/:id/access-map`）。この画像はGoogle Directions APIが返す実際の道路上のルート（polyline）をStatic Maps API経由で描画したものですが、Directionsが使えなかった場合は出発地点〜目的地を結ぶ直線にフォールバックします（実際の道なりではない点に注意）。Static Maps APIが未設定・呼び出し失敗の場合は、画面側で簡易な概略図（点線のプレースホルダー）に自動で切り替わります。5モードのうち実際にAPIで取得できるのは徒歩または車のいずれか1つだけなので、電車・バス・タクシーの時間や運賃は距離ベースの概算です（画面にもその旨明記）。

## 投稿インサイト（自治体・企業向け）

自治体・企業アカウントは `/insights` から、自分（自治体の場合は紐づく企業の投稿も含む）の投稿の再生数・いいね数・コメント数と、カテゴリ別・投稿別の内訳を確認できます。

さらに、Instagramの「オーディエンス」に相当する視聴者の**国籍・年代別の内訳**も表示します。これは `ReelView` テーブル（`backend/prisma/schema.prisma`）に記録される閲覧ログと、`User.nationality` / `User.birthYear`（登録時またはSettingsから**任意**で入力）を突き合わせて集計したものです（`GET /api/reels/mine/demographics`）。ログアウト中の視聴や、国籍・生まれた年を登録していないアカウントによる視聴は「不明」として分類されます — Instagramなどと同様、自己申告データがある範囲でしか属性を特定できない設計です。

メールアドレスからは年齢・国籍いずれも推測できないため（ドメインだけでは国籍の判定精度が低すぎる）、新規登録画面では `geoip-lite`（オフラインのIP→国データベース、外部API呼び出し・APIキー不要）でIPアドレスから国籍欄の初期値をおおまかに推定し、プルダウンに仮選択した状態で表示します（`backend/src/services/geoLookup.ts`、`GET /api/auth/suggest-nationality`）。あくまで初期値の提案であり、本人はいつでも変更・未選択にでき、保存もされません。生まれた年はこの方法でも取得できないため、引き続き完全に自己申告です。設定画面のプロフィール欄からも、国籍・生まれた年はいつでも編集できます（一般ユーザーアカウントのみ）。

## 多言語対応

i18next / react-i18next を使い、日本語・英語・中国語・韓国語に対応しています（`frontend/src/locales/`）。対応範囲はアプリのUI文言（ボタン・メニュー・フォームラベルなど）のみで、自治体が入力する説明文・投稿キャプション・都道府県名などのユーザー/実体データは翻訳されません。設定画面（`/settings`）の「表示言語」から切り替えでき、選択言語は端末のlocalStorageに保存されます。
